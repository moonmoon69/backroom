# The agents file and skills

The instructions file Backroom writes into a project's folder, and the skills you can name to members.

## The agents file

An agent should work the way its project asks, whoever gave it the work. So Backroom puts a short file in each project with working habits in four sections: **Approach**, **Working on an assignment**, **Validation** and **Documentation**. The text is the template below. It says nothing about routing, models or how a harness does the work: routing is the Consigliere's, and the rest is the harness's own.

**What Backroom writes, and when.** Only when a room is created (with **+** on the overview), in the project's folder, and only once per folder:

| The project's folder has | Backroom writes |
| --- | --- |
| neither `AGENTS.md` nor `CLAUDE.md` | `AGENTS.md` with the habits, and a `CLAUDE.md` holding the one line `@AGENTS.md` |
| `AGENTS.md` and no `CLAUDE.md` | the one-line `CLAUDE.md`, so Claude reads the project's own `AGENTS.md` too |
| `CLAUDE.md` and no `AGENTS.md` | nothing: the project has instructions of its own |
| both | nothing |

In every row, a project's own instruction file (`AGENTS.md`, `AGENTS.override.md`, `CLAUDE.md` or `.claude/CLAUDE.md` in its folder) that is a plain file git ignores is carried into new worktrees, as **Kept out of git** below says: a new worktree would otherwise have no rules file.

`CLAUDE.md` counts as there in any capitals, as `.claude/CLAUDE.md`, as a link (even one to nowhere), or when git tracks it and it was deleted in the folder. `AGENTS.md` counts as there only under that very name, as a file or a link to one; when the folder has it in other capitals, has `AGENTS.override.md` instead, has a link to nowhere or a tracked one that was deleted, Backroom writes nothing. In a project folder below its repository's top, any of these files in a folder between them (the top included) is the project's own instructions, which Codex and Claude read from there: nothing is written either. The default names the project's checks from its package scripts (`check`, else `typecheck`, `lint` and `test`, run with the package manager its lockfile names) and its Makefile (`check`, else `lint` and `test`), "and whatever else its README asks for"; with none of those it points at the README and the package scripts. Its text has one source, `DEFAULT_AGENTS_TEMPLATE` in [`src/app/agentsFile.ts`](../src/app/agentsFile.ts), a template whose placeholder `{checks}` stands for that checks phrase, and whose line `{skills}` is one line per skill pack with a standing line ([Skills](#skills)), pstack's pointing at its poteto-mode by default, and is left out (no blank line in its place) when no pack has one. Its last line says: "Backroom wrote this file when the first room was made for this project. It is the project's to edit; Backroom changes it only when you apply the current default from Settings → Agents file."

Projects that have rooms already get nothing until a new room is made there. Nothing is written when Backroom starts, when a member is seated or when a project is added. A room waits a few seconds at most for this; past that it opens, and the writing goes on. The switch in **Settings → Agents file** (on by default) turns that automatic writing off; it governs nothing else, and Apply (below) works with it off.

**What it never does.** In the project's working tree it never overwrites or edits a file by itself (each file is created exclusively: one that appears meanwhile is kept as it is, and no link is followed; the one exception is your Apply, below) and never creates a folder; inside `.git` it edits only `info/exclude` and adds at most the hook, creating `info/` and `hooks/` when they are missing. It never commits, never edits `.gitignore`, never pushes, and never installs a git hook over one, where the repository sets `core.hooksPath`, or for a project that is not its repository's main checkout. It never writes in a folder that holds others: the home folder or one above it, a folder with another of T3's projects below it, or a folder outside git with a repository below it (directly or one folder further down), since Claude Code and Cursor read these files from every folder above the one they work in, and the file would reach every session below. A folder that is not on Backroom's machine is left alone, and so is a folder git cannot say is a repository or not (git missing, a timeout, an ownership refusal, a worktree whose repository moved); the next room tries again. A project in a subfolder of its repository whose path holds characters other than letters, digits, spaces and `. _ @ + - /` gets nothing: its files could not be listed to git as they are. Once it has written in a folder it never writes there again: a file you remove stays removed, also when the project is removed from T3 and added again.

**The template, and changing it.** **Settings → Agents file** opens one dialog: the switch, the template in a textarea with **Save template** and **Reset to default**, and the projects already written. A saved template is kept in the service (the `kv` table, `agentsFile.text`); `{checks}` in it is filled per project, more than once if it is there more than once, and a template without it is written as it is. `{skills}` on a line of its own becomes the packs' standing lines, one each, or goes when no ready pack has one; a template without it gets none. Since the rendering follows the packs, a change of a standing line (or a pack becoming ready) shows the projects already written as **differs**, and Apply pushes the new line in or takes the old one out, as with any change of template. It is meant to fit any project and any harness: routing and models belong to the crew and the Consigliere, not here. The file is written once, when a project's first room is made, so a change reaches only projects written afterwards: a project already written keeps its file until you apply the new template to it.

**Each project's state.** Below the template the editor lists every folder where Backroom wrote `AGENTS.md` (a project where it wrote only `CLAUDE.md`, or nothing, is not listed), with its folder and its state against the saved template rendered for that project, its checks read again: **same**, **differs** (edited in the project, or written from an earlier template), **removed** (the file is gone; Backroom does not write it again), or **blocked**, with its reason (the folder is not on this machine or leads elsewhere now, a link put in its place or above it, or `AGENTS.md` is a link now, a folder, a file another name is hard-linked to, or cannot be read; never shown as removed). On the overview, a project whose file differs has a quiet **AGENTS.md differs** mark on its heading; it opens the diff. The page reads the states (`GET /api/agents-files`) when the overview opens and again when the editor or a diff dialog closes.

**The diff, and Apply.** **Show diff** (or the mark) shows the project's file against the saved template rendered for it, the project's lines as − and the template's as +, drawn as the Git tab draws a diff; it uses the saved template, never an unsaved draft (Show diff and Apply wait while the textarea has changes: save first). **Apply**, at the end of the diff (the list's **Apply…** opens the same diff, so you apply only what you have seen), replaces the whole file, the project's own wording included, with the saved template rendered for it; nothing applies without that click. It is bound to what you looked at: the diff carries a digest of the file and of the rendered template, and Apply is refused with "the file changed since you looked at it: open the diff again" when either changed since. It writes only where Backroom has a record of writing `AGENTS.md`, in a folder on this machine (and, for a throwaway service, under its own folders), and only through a handle on a plain file of its own: opened without following a link and without creating it, then checked to be a regular file with no other name, its folder still the recorded one (links resolved) and its name still giving that very file. So it never writes a file that is missing, never through a link, swapped in or not. It never touches `CLAUDE.md`, never commits, and never edits the exclude file or the hook; worktrees that already hold a copy keep theirs (copy it into them by hand if you want it there).

**Kept out of git.** In a git repository, Backroom lists the files it wrote in the repository's own `.git/info/exclude`, between two marker lines (`# >>> Backroom agents file` and `# <<< Backroom agents file`), as `/AGENTS.md` and `/CLAUDE.md` (with the project's folder in front when it is a subfolder of its repository); the file's other lines stay as they were. That file is the repository's own, shared by its worktrees and with nobody else: `git status` shows nothing to add, nothing needs committing, and other people using the repository never see the files.

The same block lists a project's own instruction files that git ignores (the project keeps them out of git itself, through `.gitignore` say), so the hook below copies them too; the note on the page says nothing of it when nothing was written, and the service's log does. Once per folder, like the writing, and such a project is not listed in **Settings → Agents file**. A block that lists them already, with the hook there, is left as it is and leaves no record. A file git tracks is not listed, since every worktree has it, nor is one that is untracked and not ignored: listing that would hide it from `git status` while the project may be about to commit it. A link is not listed either, and a `.claude/CLAUDE.md` is copied only into a worktree that has a `.claude` folder.

**Copied into new worktrees.** A new worktree holds only what is committed, so Backroom installs a small `post-checkout` hook in the repository's `.git/hooks` (its worktrees share it). On `git worktree add`, which is how T3 makes a member's worktree, the hook copies the files listed after Backroom's start marker from the main checkout into the new worktree when they are missing there, never over a file or a link, and never fails the `git worktree add` (a folder the new worktree lacks is skipped); a branch switch does nothing. Backroom installs it only when the repository has no `post-checkout` hook and sets no `core.hooksPath`; otherwise it installs nothing. To have the files copied then, add this line to the repository's own post-checkout hook, if it is a shell script, before any `exec` line (the hook Backroom installs runs the same line); a hooks folder the repository tracks (`core.hooksPath`) is shared with everyone who uses it, so the line would reach them too:

```sh
case "$1" in *[!0]*) ;; *) m=$(git worktree list --porcelain | sed -n '1s/^worktree //p'); sed -n '/^# >>> Backroom agents file/,/^[^/]/s|^/||p' "$(git rev-parse --git-path info/exclude)" | tr -d '\r' | while IFS= read -r f; do [ -e "./$f" ] || [ -L "./$f" ] || [ ! -f "$m/$f" ] || cp -- "$m/$f" "./$f" 2>/dev/null || :; done ;; esac
```

A worktree that exists already gets nothing: copy the two files into it by hand if a member works there. Nor does a project that is not its repository's main checkout (a linked worktree, a submodule) get the hook: it copies from the main checkout, where nothing was written. When the exclude file or the hook could not be written, the note says so, and Backroom does not try again.

**Undoing it.** Delete the files Backroom wrote, Backroom's block in `.git/info/exclude` and, if Backroom installed it, `.git/hooks/post-checkout`. Files of the project's own that the block listed stay as they are, ignored by whatever ignored them before. To commit an `AGENTS.md` of your own there later, delete Backroom's block first: git skips the files it lists.

**What the page says.** A room created from the overview opens as ever, with a note saying what was written and where, that it is kept out of git, and whether the hook copies it into new worktrees or the line above is needed (when the writing is done within the few seconds the room waits for it).

**When members read it.** A harness reads its project files when its session starts: a member already seated reads the new file in its next session (after a reseat, say), and one seated in a new worktree made after the hook was installed has it from its first.

**Which harness reads which file.** One `AGENTS.md` holds the text, and `CLAUDE.md` imports it rather than copying it: a copy would drift, and Cursor, which reads both, would load the text twice.

| Harness | Reads from the project | Gets the habits from |
| --- | --- | --- |
| Claude Code | `CLAUDE.md` and `.claude/CLAUDE.md`; `AGENTS.md` only where no CLAUDE.md is ([docs](https://code.claude.com/docs/en/memory)) | `CLAUDE.md`, whose line `@AGENTS.md` imports it |
| Codex | `AGENTS.override.md`, else `AGENTS.md`, in each folder from the git root down to the working folder, 32 KiB in all ([docs](https://developers.openai.com/codex/guides/agents-md)) | `AGENTS.md` |
| Cursor | `AGENTS.md`, `CLAUDE.md` and `.cursor/rules` ([docs](https://cursor.com/docs/context/rules)) | `AGENTS.md` (the one-line `CLAUDE.md` is a harmless rule to it) |
| Antigravity (Gemini) | `AGENTS.md`, `GEMINI.md` and `.agents/rules` ([docs](https://antigravity.google/docs/rules)) | `AGENTS.md` |
| OpenCode, Pi, Grok | not verified | |

T3 starts Claude with its default setting sources, project files included, and Cursor with its project settings (read in T3 0.0.46's code), so members read these files as they would in T3 Code.

Backroom's own repository keeps its `AGENTS.md`, with its real checks, and the same one-line `CLAUDE.md` out of git like any other project's: listed in its `.git/info/exclude` and copied into new worktrees by the same post-checkout hook.

## Skills

**Settings → Skills** is where you say which skill to use when. It has two parts: the **roster**, everything you can name to a member with your lines on it, and the **packs**, the git repositories of skills Backroom keeps for you. The code is [`src/app/skillRoster.ts`](../src/app/skillRoster.ts) and [`src/app/packs.ts`](../src/app/packs.ts); the fixed facts (pstack, the skill folders, a row's identity) are in [`src/domain/skills.ts`](../src/domain/skills.ts).

**The roster.** One list, grouped by kind: **Room directives** (`/now`, `/add`, `/remove`), **Harness commands** (each provider's slash commands as T3 lists them; Claude's skills are among them, since T3 lists Claude's skills as commands), **Skills** (the skills list T3 reports per provider apart from its commands, such as Codex's system and plugin skills) and **Pack skills** (a pack's skills Backroom has linked). A row is one source: a command is its provider and name, a skill T3 lists is its provider, scope, path and name as invoked (a plugin's prefix kept, `openai-templates:artifact-…`), and a pack's skill is the pack and the skill's folder in it. A display name such as "Analytics Dashboard" is shown beside the name, never as its identity, so the same command on Claude and on Codex is two rows. A skill T3 lists whose real path is a pack's skill folder (found through Backroom's link) is that pack's row, for every harness that reports paths. Claude reports none (T3 lists its skills as slash commands), so a Claude command is taken for a pack's skill only when Backroom linked that skill into a folder Claude reads and the command's name and description are the skill's link name (see **Links**) and frontmatter description; every other command, a native one of the same name included, stays a harness command and keeps its slash. A skill its harness turned off is left out. Each row shows its source, the crew members who have it (those whose harness T3 lists it for), the author's line greyed, a restriction where the author set one (**user-invoked only**: its author lets only you invoke it; **model only**: no slash command), and two fields of yours with a crew member's cap of 300 characters, **use when** and **avoid**, saved as you leave them (`skill.hint.set`, kept in the `skill_hints` table by the row's identity). They start empty: the author's line is never copied into them. A pack skill's row also says where it is linked, with who reads each folder, and its real source path. T3 lists what a harness found when its session started, so a skill linked now reaches a seated member after a reseat; until T3 lists it, its row says no harness lists it yet. While T3 does not answer, its rows are missing and the dialog says why.

**Packs.** A pack is a git repository in Backroom's data folder, at `data/skills/<folder>` (under the data folder's real path; the `packs` table holds its name, URL, folder, pinned commit, standing line, last check and last error). **pstack**, Lauren Tan's skills for rigorous agent work (MIT, in [cursor/plugins](https://github.com/cursor/plugins)), is there from the start, in `data/skills/cursor-plugins`: a service that had Poteto mode keeps that clone (sparse to `pstack/` and `harness/pstack/`, not cloned again), pinned at its checkout. A fresh service clones it whole (`ROOMS_PSTACK_REPO` names another source). **Add pack** takes a repository URL (https, ssh, git or file, or an absolute path), clones the whole repository into a temporary folder beside its place, and moves it there only when it holds a tracked `SKILL.md`; it is pinned at the commit cloned, and its name is the repository's. A pack's skills are its tracked `SKILL.md` files present in its checkout, named and described by their frontmatter. **Nothing is enabled by finding it**: a skill reaches a harness only through a link you place, also after an update brings new skills. Backroom never runs a pack's scripts or a setup step (no hook runs in its git commands, and no `ext::` transport); a skill that needs a runtime or an MCP server says so in its own README, and you or a member install that once.

**Links.** Under each pack's skills, every skill has a tickbox per skill folder it may go into, each labelled with who reads that folder:

| Folder | Read by |
| --- | --- |
| `~/.claude/skills` | Claude, Cursor, OpenCode |
| `~/.agents/skills` | Codex, Cursor, OpenCode, Pi |
| `~/.grok/skills` | Grok |

A folder is shared by everyone who reads it: a link placed for Claude reaches Cursor and OpenCode too, so nothing here is per harness. A tick places a symlink named after the skill (its frontmatter name when that is a plain folder name, as the skill's own installers name it: Taste's folder is `skills/taste-skill`, its link `design-taste-frontend`; its folder's name otherwise), pointing at the skill's folder by its real path (the skill folder is made when missing); unticking removes it. pstack's two trees keep to their folders: its Claude Code copy (`harness/pstack/claude-code/skills/`, with pstack's adapter) goes only to `~/.claude/skills`, its own tree (`pstack/skills/`) only to the other two. Refused with the reason and nothing changed: a name already in the folder that is not Backroom's link to that very skill (your own skill, a file, or a link of anyone else's, another pack's same-named skill included), and `synced`, which Claude's account sync owns. Unticking removes only Backroom's link to that skill. A skill that walks up from its own folder to find files outside it finds the link's folder, not the pack's: its real path is on its roster row.

**Updates.** Every pack stays at its pin. Backroom looks each hour whether a day has passed since a pack's last check (or the check failed); then, and on **Check now**, it fetches, and moves nothing. When upstream's commit differs from the pin, the pack says **Update available** with that commit; **Show what changes** gives the files with their status, git's stat, each `SKILL.md` whose frontmatter description changes (before and after, highlighted), the links taking it would remove, and the full diff (cut at 2 MB); a sparse clone's diff keeps to the paths it holds. **Take update** checks out exactly the commit you looked at, even when upstream has moved on since (the newer one is offered next), and pins it. Only a tracked file changed in the pack stops it ("local changes to tracked files…", nothing moved); untracked files, such as a marker a skill writes beside itself, stay, unless the update brings a file of the same name, which refuses it naming the file. A linked skill that stops being one (its `SKILL.md` gone, or its folder) loses Backroom's links to it: at **Take update**, which names them first and says so after; at an install; and at the hourly look, for a checkout moved by hand. Its roster row goes with them; your lines on it are kept, as **Remove** keeps them. One git operation runs at a time, links and removals included; while one runs, the agents file and the briefing read each pack as it was before it moved anything. Backroom refuses, with the reason shown and nothing deleted or moved, a pack folder (or `data/skills`) that is a link, one whose `.git` is a file or a link, a folder there that is no clone, and one whose git top level is another folder (the data folder lives inside Backroom's checkout). **Remove** takes Backroom's links to the pack's skills out first, then its folder and its row (your lines on its skills are kept, for a pack added again); it is refused the same way.

**Standing lines.** A pack may have one line every seat is given, with `{folder}` for its folder: in each project's agents file (the template's `{skills}`, see [The agents file](#the-agents-file)) and in the briefing's **Skills** section, for every seat, with the pack's commit and folder (`rooms-board rules` prints it). pstack's offers its two presets: **Principles and reply rules**, the default, to follow poteto-mode's principles, reply and comment rules with its triggers and playbooks only when an assignment names them (the Consigliere routes work and names the playbook a job needs, so a member running them on its own would duplicate the room), and **The whole mode**, to read and follow poteto-mode for any non-trivial job; **No line** is none. A change of the line shows the projects written as differing (Apply pushes it), and a seat gets the changed section with its next briefing, or a short note that it no longer applies when no pack has a line.

**The composer.** After a member's name, `/` lists what every member addressed has, grouped as the roster is, with your **use when** line under each entry (the author's line where you wrote none) and your **avoid** line beside it; entries with an avoid line sink to the bottom of their group. A skill only the model may invoke is not offered; one only you may invoke is. Picking a skill writes `using the <name> skill` where the cursor is, so the message stays a briefed request and the member invokes the skill inside its turn; picking a command or a directive writes it with its slash ([T3 slash commands](messages.md#t3-slash-commands)). The list reads the roster again each time it opens.

**The Consigliere.** His briefing carries, once each, every skill (and command) you wrote a line for: its name and source, your lines, the crew members who have it, and **user-invoked only** where T3 says so, so he names one in an assignment ("using the … skill", to a member who has it) the way he seats members by their lines, and one only you may invoke only when you ask for it. It is capped at about 2,000 tokens (8,000 characters): entries go whole, those with an avoid line kept first, and the rest are counted ("N more with the user's lines are in Settings → Skills"). It is sent again when it changes, who has a skill included, and not while T3 cannot say who has them.
