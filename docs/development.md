# Development

How to work on Backroom itself: the commands, the browser rehearsal, where the code is, and how the service works.

## Commands

```sh
npm run typecheck                # service types
npm --workspace web run typecheck
npm test                         # acceptance tests against the fake adapter
npm run check                    # typecheck + tests
npm run dev                      # service with --watch
npm --workspace web run dev      # Vite on :5173, proxying /api to :4400
```

UI text uses one type scale, defined at the top of `web/src/styles.css`: `--text-xs` 11px (meta), `--text-sm` 12px (secondary), `--text-md` 13px (list rows, menus), `--text-base` 14px (messages, inputs), `--text-lg` 16px (titles), `--text-xl` 18px (brand). Use those rather than literal sizes; icons come from `web/src/components/icons.tsx`.

Tests never touch a real T3 server, and write no agents file outside folders they make. To try UI changes safely, run a demo instance on another port (`ROOMS_ADAPTER=fake ROOMS_PORT=4401 ROOMS_DATA_DIR=/tmp/rooms-demo npm start`); `ROOMS_FAKE_PROJECT_DIR` points its demo project at a scratch repository, for a rehearsal too. The habits for anyone working here, agents or not, and the checks to run before reporting ready are in `AGENTS.md`, which this repository keeps out of git as Backroom keeps any project's ([The agents file](agents-file-and-skills.md#the-agents-file)).

## The browser rehearsal

The browser rehearsal (`scripts/rehearse.ts`) plays the page in one of the shared browsers against a throwaway service of its own (the fake T3, its own data folder, the page last built with `npm run build:web`), and checks each state in the API and on the page:

```bash
node scripts/rehearse.ts --step ui|room|keys --as <rooms-browser key> --port 4511   # one step, on a free port
node scripts/rehearse.ts --step all --as <rooms-browser key> --port 4511            # the three at once, on 4511-4513
node scripts/rehearse.ts --step keys --list                                         # a step's states, numbered
node scripts/rehearse.ts --step keys --as <key> --port 4511 --only 47 --only "Esc closes"
```

- **Its tab** opens on `http://rehearse-<port>.localhost:<port>` (Chrome takes any `*.localhost` to this machine), not `127.0.0.1`: a site of the run's own gets a renderer of its own, so a crash in a run takes no other tab with it, another run's or anyone's (`REHEARSE_TAB_HOST` names another host).
- **The steps:** `ui` and `room` play a room's story (the turn relay, notices, the Browser panel); `keys` drives the page by keys alone (focus, scrolling, layout, the key bar). Run the step that covers the change: keys for keyboard, focus, scroll and layout; ui and room for what the engine and the page show.
- **`--step all`** starts the three together, each on a port of its own (`--port` and the next two) with its data under `--data` (default `data/rehearse-all-<port>/<step>`; one step's is `data/rehearse-<step>-<port>`, so runs side by side never share a folder), keys in a browser of its own (`--keys-browser`, default backroom-dev; ui and room in `--browser`, default general). It prints each step's result and exits non-zero if any failed; each step's output is in `<step>.log` there (or under `--out`). A step that fails or is stopped (Ctrl-C stops them all) has its service and tabs cleaned up after it.
- **`--only <state>`** (as often as wanted) checks just the states it names: a number from `--list` (under `--step all`, that number in each step), a range (`12-15`), a `/pattern/` or part of a name. Each step is cut into sections that stand on their own (the room quiet, the page at a known place); a run jumps to the section of the first state named, its setup makes through the API what the section reads (and checks it is there) and brings the page to where the section starts (every section played after it makes too what it reads that the skipped ones would have made, nothing twice), the states before the one named are played without their screenshots and console reads, and the step stops after the last state named. The states of each step's first section need the whole story before them: ui 1-14 and room 1-14 (keys' first section is its start). For those, `--until <state>` plays the step up to the state with every check on, in the same time. **`--until <state>`** plays a step as always and stops after the state it names. `--help` prints every flag.
- **A failure** ends the step and leaves the page as it was beside the states' screenshots (under `--out`), before its tab closes: `NN-failure.png` and `NN-failure-snapshot.txt`, the page's text with element uids.
- **A fails-without-the-fix proof on the page** (where no unit test can show it): in a worktree of the fix's commit (whose scripts have the flags and the state), take the fix out of the product with `git checkout <the commit before the fix> -- <the files of web/ or src/ the fix changed>` when the fix is the last change to those files, else with `git show <the fix's commit> -- <those files> | git apply -R --3way` (a later change to the same files needs the three-way merge), and delete a file the fix adds. Then `npm install`, `npm run build:web` and the state with `--only`: it must fail at that state.

## How it works

- **The journal.** Each room's board is an append-only journal (`data/board.sqlite`): requests, corrections, cancels, notes, answers, notices, runs. Everything the page and `rooms-board` show is read from it, and a restart folds it back to where it was.
- **Delivery.** A member's requests go to its thread as one T3 turn. The turn's message is a **briefing**: the standing sections when the thread needs them, then the work (its requests and corrections, the answers to what it asked, the posts it has not seen, long ones shortened to a pointer that `rooms-board read` prints whole). Each post is delivered once. What a turn was sent is frozen before it is sent, so the run's page shows exactly what T3 received.
- **Where everyone works.** Every briefing says which folder and branch are the agent's own (its thread's T3 worktree, or the project folder, read with git when the briefing is made), where each other member works, and who shares its folder. It asks the agent to deliver its work in its own folder and branch, because T3 and Backroom follow changes only there. Extra worktrees are welcome for parallel work (sub-agents, experiments), based on the agent's branch (a harness's own worktrees often start from origin's default branch instead), with what it keeps merged back before it finishes and any it leaves listed in its Handoff. It also asks the agent to read the others' work with git without switching (`git diff <your branch>...<branch>`, `git -C <folder> diff`); never to edit another member's folder; and, when sharing a folder, not to switch branches, stash, reset or clean.
- **Completion.** In T3 a thread's work is a sequence of runs, each started by one message. T3 names that message on the run, and names the run on a message sent into it while it runs (T3's steer), so Backroom finds each turn's run by the id it gave its message. The engine host reads every seated thread each tick (from T3's thread stream while it holds: see below), and at once when one changes: the run's own status says queued, running, waiting on you, completed, failed or interrupted, and its last assistant message is the member's final reply, which answers the requests the turn was given. A run T3 never takes fails visibly, with one notice. Sending again with the same command id never starts a second run: T3 keeps a receipt for each command.
- **Live pages.** Each open page keeps one stream from the service (`GET /api/events`, server-sent events): a room changed (any append to its journal, or a change the service announces), T3's projects or threads changed, a thread the page shows changed in T3, T3 stopped or started answering. The page reads again what an event names (T3's threads changing: the overview, T3's projects and the open room's snapshot), and reads everything again whenever the stream reopens (a phone drops it while the app is in the background) or the page comes back into view. While the stream is open its timers only back it up, every 60 s; while it is closed they read more often: the overview every 5 s, the open room every 4 s while it is busy and 15 s otherwise, the service's status every 30 s (`web/src/App.tsx`). T3's side comes from T3's own stream (the shell feed below): a change it applies reaches the pages at once, and while T3 keeps streaming (every item of a running turn moves a thread) once more at the end of each 2 s; the feed dropping is T3 not answering, told at once, and its reconnect T3 answering again. On the fake T3, which has no stream, it is checked every 2 s while a page is open. The overview's T3 banner and the T3 chip both say what the service says: the banner shows while it says T3 is down, as "T3 is not answering", or, once T3's lists have been read directly during the outage, as T3's live feed being down with its lists possibly lagging; only the service saying T3 is back clears it. A thread's own view, a member's thread over its room and the room's desk (each member's live turn, context and changes) read it again on each change of a thread they show, at once (T3's thread streams, below); their timers are a 60 s fallback while the stream is open and the service says the thread's changes are pushed, else every 1.5 s for a thread that works and 2.5 s for the desk while a member works. The Git tab, costs, the browsers and the presets keep timers of their own.
- **Turns the room did not start** (typed in T3 Code, or the agent's own continuation) are imported as follow-ups on the member's request, and wake the Consigliere.
- **T3's shell, as T3 streams it.** Backroom keeps T3's projects and threads live from T3's own stream of them (`orchestration.subscribeShell`, on a WebSocket of its own, reconnected with backoff when T3 goes away). The engine host and the page read them from there with no HTTP snapshot (after a command, until the stream shows it: a second at most), and a change to a member's thread wakes the host at once rather than at its next tick (a change that only moves the thread's time, which T3 streams for every item of a running turn, does not). While the stream is not live (before its first snapshot, or until T3 is back), reads go to T3's HTTP snapshot. Archived threads are on neither: T3 streams none and its snapshot lists none, so they are read with its `getArchivedShellSnapshot` call when asked for, afresh after every command and every change the stream shows. `GET /api/status` says which, under `t3.feed`. One limit is T3's: its stream skips updates that only move a thread's time, so that time can be up to 5 s behind until the thread's next change, enough for two threads updated in the same few seconds to trade places on the overview.
- **T3's threads, as T3 streams them.** A thread's detail (its runs, messages, items and requests) is read from T3 once per change, and that read serves every reader until the next change. On the shell feed's socket Backroom subscribes to each watched thread (`orchestration.subscribeThread`, one request each, every chunk acknowledged, interrupted when the watch ends). A thread is watched while a room seats it, or while a page has read it in the last minute (the thread view, a member's thread, the desk; each read renews it, and the stream outlives the minute by 30 s, so the page's own fallback read keeps it); the overview's lines about threads outside rooms watch nothing. The subscription starts after the thread's latest read, so T3 replays the few events since rather than its snapshot (megabytes for a long thread); T3 still sends the snapshot (only its sequence is used) when the gap is too long to replay, as after a long outage, or when the thread has no read to start after because its first read failed. Its events are used only to say that the thread moved: the first change after a quiet spell is read at once, then at most one read per 2 s per thread while it keeps changing, and one after the last; the read is told once it is in (the engine host wakes, open pages read again). A read made by anyone between two of those serves the latest read, up to that throttle behind T3 during a busy turn, but never older than what the thread's shell shows (its status, runs, request or background work: a read below that is made again, so the engine host imports from the detail what the shell says has happened); after one of Backroom's commands on the thread the next read is made at once. While T3 refuses a thread's stream (logged, asked again later), while the feed is down, and until T3 has replayed what came since a reconnect, the thread is read from T3 on each call, and its pages read at their pace without a stream. A watched thread holds its latest read of each kind it was read in (its recent window, and its whole history when the engine needed it) while it changes, and only the newer one once it has been quiet for 30 s: about 2.7 MB of JSON for a long thread. `GET /api/status` counts the watched threads, their live streams and those T3 refuses under `t3.threads`.
