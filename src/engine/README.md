This directory implements isolated slices 1–3, accepted incremental storage P, and the ordinary/background usability amendment U of the board-driven engine. It has no live callers and imports no old Task, production database or scheduler code. The isolated store uses Node's built-in SQLite, as the project already does. The room event log is the only causal authority. Requests, answer claims, ownership, return routes, cursors, subscriptions and recovery records are disposable projections.

`decide(log, command)` returns `{ expectedSeq, events, outcome }`. The input is one room's contiguous committed event log. IDs, authenticated principal, budgets and provider evidence come from the caller. The function does no I/O, dispatch, clock reading or random ID generation and never modifies its inputs. `fold(log)` rebuilds projections. `unread`, `deliveryDisposition` and `selectPrefix` derive delivery from those events. A projection can be discarded/rebuilt; modifying a returned Map is never a durable action.

Slice 2 must read the room head and append the **whole decision batch atomically**, under the same room transaction/compare lock. A head mismatch requires deciding again against the winning log. Maintain unique event IDs, command identities, provider source keys, successful request claims and unresolved seat reservations as rebuildable constraints. A command may append output, receipt confirmations, notices and run end in the same transaction. Do not append individual events separately. Requests use their event ID; other generated event IDs are `command.id/ordinal`. Reserve that namespace. Caller IDs must be stable and unique within the room. An idle/duplicate decision has no events; it need not be persisted as another job.

The actor `$system` is reserved for authenticated storage/adapter operations. `$user` is the authenticated user, never an agent impersonation. Seat IDs starting with `$` are rejected and never reused; provider threads are not reused by new seats. There are no aliases in this interface. The store must load trusted events produced by decisions; `fold` checks log order, duplicate source/claim identities and unresolved runs, but is not a wire-format validator or a substitute for authentication. Slice 4 must validate incoming payloads before this typed boundary.

Requests capture owner, original return endpoint, parent and root identity. Every request has its own unique terminal claim; reviews/questions are real descendant requests, not return jobs. Corrections keep the original request and accumulate mandatory amendment content. At output time an unseen correction supersedes the proposed answer; cancellation/ownership transfer retains it as late. Closed work cannot be corrected/reopened. Return endpoints change only in a transfer event naming all open awaited requests; emitted result recipients and claims remain immutable. A source key identifies one provider emission, independently of an answer claim. A superseded/late/progress emission never reserves the terminal claim. Early answer and later provider final therefore coexist as one answer and a non-actionable output.

There is **no normal-final completion default**. Provider imports must choose `answer(requestIds)`, `yield`, `progress`, `error(requestIds)` or `silent`. A turn end releases a run and commits its exposed input prefix; it does not finish open requests. `answer` is an explicit completion attempt. It can claim only exposed/associated work owned by the same immutable seat, with no unseen correction, cancellation, open causal descendant, unresolved associated control, or pending/uncertain associated activity. Independent co-batched requests can finish separately. A blocked attempt is retained with `pending_activity`/`superseded`/`late` outcomes and leaves the request open. There is no speculative completion inference from prose.

Known child/background work is registered with an explicit activity ID, originating run and distinct request associations before completing its parent. Ordinary progress, activity output and provider terminal output never resolve it. Only `activity_status` with evidence or `output(activityCompletion: done|failed)` resolves that known activity. Later output remains correlated to that exact activity/run even after the provider turn ends or other work arrives. Unassociated native output is stored as a visible orphan with one bounded attention notice; it never attaches to the latest request. No-work-pending means the fold contains no pending/uncertain associated activity, open descendant request, or unresolved associated control. That is knowledge of reported activity, not proof that an unreported external process cannot exist. The slice 3 adapter must surface native pending work and association evidence; this core cannot discover it.

An envelope contains every required addressed input through its watermark, including full inherited transfer/retry content. Open owned request roots, return addresses and corrections are resumable mandatory context as of that watermark. Other history is optional context through the same bound. Budgeting counts serialized UTF-8 envelope bytes; the caller allocates a byte allowance after provider overhead and optional context. The oldest oversized body blocks visibly once per blocking input; it is never skipped. Rendering and model-token sizing remain slice 3/4 work. A run reservation freezes payload and command/message IDs and permits at most one unresolved run per seat. Prepared/sending/uncertain/rejected runs hold that reservation; no cursor moves on dispatch acceptance.

`sync` offers a complete prefix and a SHA-256 receipt over run, receipt ID and envelope. An offered receipt has no delivery effect. The provider must echo the exact receipt on output, or the adapter must use `confirm_sync` with durable exposure evidence. Overlapping confirmations cannot retract progress; later inputs survive. Arbitrary board reads and citations are never acknowledgements. A terminal event atomically commits the exposed prefix, records failure if appropriate and releases the reservation. It preserves frozen/confirmed inputs for explicit retry. No timer retry exists; an uncertain reservation cannot be replaced. This slice represents definite rejection and deliberate retry, but does not implement durable dispatch/resend reconciliation.

Live questions bind the originating run and provider runtime request ID. Their authorized answer is `runtime_reply`, with a unique answer claim, retained body and stable response command ID. It never wakes the worker or changes its cursor. Prepared/sending/uncertain controls require reconciliation; unknown responses cannot be blindly resent. A terminal provider run does not settle them. A proven accepted late receipt stays accepted; a proven closed/unapplied reply becomes obsolete with one bounded attention notice retaining the answer. Permission replies require the actual question owner (`$user` for user approval). Message-mode questions instead yield and receive an ordinary result input through `user_answer` or correlated member output.

Ordinary progress and notes are observable context. Only an explicit named milestone subscription makes matching progress addressed input. Recipients are frozen at append time; disabling a subscription does not erase already-addressed content. Multiple milestones use the same prefix/cursor mechanism and coalesce in one run. `silent` has an empty body, consumes the prefix and emits no routed acknowledgement. Progress, own output, operations and open work do not otherwise trigger runs.

Failure notices are bounded once per run/activity. Notice-only (including subscribed status-only) failure is a visible non-waking recovery error, even when old open work appears as context. Fresh failure scope comes from delivered real inputs and explicitly selected resumed work; activity failure scope comes only from its causal associations. Cancellation may interrupt a co-batched run without completing unrelated requests. Interrupt command acceptance does not release the reservation. Retrying failed input is an explicit board control carrying required original content, never a synthetic work row. Undeliverable and orphan notices do not recursively report notice-delivery failure.

`transfer` requires a fresh seat/thread, exact open owned/awaited identities, local known quiescence and a provider proof reference. Known unresolved runs, controls and pending/uncertain background activities block it. One event retires the old seat, changes named ownership/future return routes and carries every unread input through cutoff C. The replacement starts at cursor C and receives transfer C+1 with that mandatory bundle. Pre-cut results are inherited once; post-cut results use the explicit new return endpoint. Old delivery is classified transferred rather than read; subsequent old-address input is undeliverable. Stale generation output cannot claim the replacement's work.

The Slice 2 store is `EngineStore` in `store.ts`, also exported by `index.ts`. It owns a dedicated SQLite file; an existing database containing unrelated tables is refused. Its schema is created only when explicitly constructed. Opening or reading never dispatches or creates a fresh run. All callers in this slice are temporary-file tests; there is no bootstrap, scheduler, API or provider wiring.

`execute(roomId, authenticatedCommand)` acquires `BEGIN IMMEDIATE` **before** reading the committed log and calling `decide`. SQLite serializes writers to the dedicated database, including across rooms. No stale precomputed decision can be submitted. A blocked writer reads and decides against the winning head once it acquires the lock. The store verifies `expectedSeq`, appends the entire batch and updates affected journal-derived indices in one transaction. Cold recovery, unexplained own/foreign changes and rebuild audit all derived rows against authoritative replay. WAL with `synchronous=FULL` is set on every store connection. Busy waiting is bounded (default five seconds); a lock-timeout caller can retry the same command identity. An exception before commit rolls back. A lost local response after commit must be recovered by replaying the same command, rather than inventing another identity.

The five tables are deliberately small in concept:

- `engine_event` is the sole authoritative append-only journal, scoped by room. Along with each domain event it records immutable command digest, original outcome, whole-batch start/count and source digest. That provenance is part of the log, needed to distinguish conflicting retries and reconstruct receipts; it is not a queue. Update/delete triggers protect ordinary journal writes.
- `engine_head` and `engine_command` are disposable head and receipt indices.
- `engine_projection` contains canonical JSON rows for folded seats, requests, runs, controls, activities, subscriptions, blocking facts and room metadata. It has no independently writable work lifecycle.
- `engine_key` enforces derived unique thread, provider-command, dispatch-message, sync-receipt, source, claim and unresolved-seat identities. Dispatch and control command IDs share one provider-command namespace within a room.

All four indices are reconstructed from `engine_event` alone, including command/source digests. `audit(roomId)` compares every stored row against a fresh fold/rebuild under one read snapshot. `rebuild(roomId)` atomically replaces indices without changing the journal. `load` returns domain events; `project` folds the journal, so changing index rows cannot change causal state. The exported domain log omits storage provenance and is not a full database backup. A mismatched head blocks further commands until rebuild; other projections are never used as decision authority. This first implementation folds/rebuilds the room on every append, trading throughput for a small, auditable contract. No scale/performance claim is made.

`execute` returns `CommitReceipt { expectedSeq, events, outcome, head, replayed }`. For a committed same-identity retry it returns the **original whole batch**, original expected head and outcome, with `replayed: true` and the current head. Returned events are receipt evidence, not a request to append them again. SHA-256 identity uses canonical lossless JSON (object key order ignored, array order retained). Reusing the same actor/command ID with different content is rejected. Callers must allocate stable unique command IDs across the room, including separate IDs for later observations. Eventless idle/duplicate/already-confirmed checks have no committed effects and create no receipt; they may be reevaluated against later input. A blocked decision that appends its first visible fact does have a durable receipt. Payload validation and principal/correlation authentication still belong before this typed boundary.

An imported source's author, exact body, causal association, explicit disposition and activity-completion declaration are immutable. Reusing a source with changed content is rejected, even with a fresh command ID. Turn-end and receipt observations may be added later with a new stable command ID for the same immutable emission. The later observation ends the same run without another output or claim. A separately learned child completion uses `activity_status` with evidence, rather than mutating an already imported emission. Ordinary event JSON preserves insertion order, so frozen envelopes and offered receipt payloads retain their exact serialized bytes and digest across restart.

Slice 3 handoff: `recovery(roomId)` is a read-only inventory of unresolved runs, controls and pending/uncertain activities. It includes prepared/sending/uncertain/rejected reservations and their original frozen envelopes/dispatch IDs. Obtain provider evidence for those exact identities; only then submit stable `phase`, `control_phase`, `confirm_sync`, `activity_status` or correlated `output` commands to `execute`. Use `project`/`load` for all history, including terminal run context and answered/open request associations. Persist `reserve`/`runtime_reply`/cancel's interrupt control before contacting a provider. Sending-phase events record an intention/evidence, not proof of provider execution. Acceptance alone never moves the cursor. This store performs no provider send, attach, reconcile, automatic retry or replacement. Local source/claim uniqueness does not establish provider exactly-once execution or external side-effect deduplication. Fake evidence in these tests is not an adapter contract.

Validation: `node --no-warnings=ExperimentalWarning --test --test-timeout=20000 tests/engine/*.test.ts`, `npm run typecheck` and `npm test`. Alongside the accepted domain/incident tests, the store tests use real temporary file databases, reopen, simultaneously open connections, competing child processes and SIGKILL before/within/after transactions. They verify whole-batch finish/transfer/control/activity atomicity, exact frozen bytes/receipts, lost commit response replay, all-index destruction/rebuild parity, unresolved reservation recovery, legitimate later input, explicit dispositions and no acknowledgement or hidden work queue. SIGKILL proves local process-loss behavior, not physical power-loss resilience or a provider guarantee. Provider receipt lifetime, external invocation/tool effects, production integration and cutover readiness remain slices 3–5.

Slice 3 adds the isolated `EngineReconciler`, `ProviderAdapter` contract, `EngineHttpT3Adapter` and explicitly synthetic `FakeEngineProvider`. None has a live caller. `HttpT3Adapter` gains two raw primitives (`engineSnapshot`, `engineDispatch`); existing application behavior is unchanged. The dedicated journal remains the sole authority. There is no second queue/table, old Task dependency, provider bootstrap or cutover.

`prepareRun(room, reservedRunId, modelSelection)` freezes the exact complete envelope plus the model/options and stable dispatch/message IDs as a `backroom.envelope.v1` text payload. The event retains the exact command JSON, SHA-256, environment ID, server version and pinned contract. Reload never rerenders that payload with current settings. The store rejects a frozen payload that drops/changes reserved input, changes thread/message/command identity or uses a queue mode. Runtime controls freeze the exact retained structured answer (`{answers:{...}}` or authorized `{decision:...}`) and original runtime-request ID; interruption always names the bound provider run, never the latest run. IDs must be globally unique within the provider environment, including across rooms and external clients. T3's same-thread receipt replay does not compare payload content; local immutable bytes are therefore necessary.

`tick(room, seatId)` makes one bounded read and reconciles the same journaled run/control. It never reserves a turn, invents an ID, queues provider input, schedules a return or retries on a timer. A serialized local `transport_attempt` records the attempt count and sending phase atomically before I/O. Concurrent ticks using the same EngineStore coalesce. Independent processes require one reconciliation owner; where a stronger adapter proves persistent same-ID dedupe and serialized receipt absence, duplicate same-ID transport packets may still be possible, without a fresh invocation. This is not an exactly-once transport/tool-effect claim. Attempts are bounded to two by default (configurable 1–5 for stronger adapters). The pinned T3 reserved policy limits MESSAGE packets to two total, identical bytes/IDs under durable same-ID dedupe; stronger idle-only adapters still require authoritative receipt absence for resend. Controls never receive the reserved MESSAGE exception. A lost response with unsupported evidence holds visibly rather than manufacturing rejection or another run.

Provider run binding requires one exact persisted user-message ID, unchanged frozen input text, the correct thread and an immutable provider run ID. Full local projections are read, not cached shell/latest-job guesses or bounded transcript windows. Missing arrays, history cursors, truncation, streaming output, conflicting identities and unknown statuses hold visibly. An unavailable/deleted provider thread is uncertainty, not absence. Later output from an old bound run or registered activity keeps its original association; stable unsolicited output with no binding becomes an orphan and one bounded attention notice. Activity identity is `JSON.stringify(["native", threadId, nativeTurnItemId])`. Slice 4 must register that exact activity through `activity_start` with explicit request IDs before parent completion; public T3 activity metadata does not carry board request identity. Discovery without that declaration holds rather than assigning it to the latest request. Native disappearance is not completion of an already-known activity.

A stable assistant message can declare `{"schema":"backroom.output.v1","body":"...","disposition":{"kind":"answer","requestIds":["request-id"]},"receipts":[{"id":"receipt-id","digest":"64 lowercase SHA-256 hex chars"}]}`. Other explicit dispositions are yield, progress (requestIds and optional named milestone), error (requestIds), and silent (empty body). Ordinary prose has no completion default. Missing declarations hold. Authenticated Slice 4 tools may also append explicit core outputs directly with proven run/activity identity; a later ordinary provider final still needs an explicit declaration/association, rather than prose inference. There is no automatic ack. Output is imported once by immutable source identity. A separately learned terminal status uses `observe_end` against an already-imported exact source, without changing the emission or reclaiming requests. Failed/interrupted terminal observations record bounded failure, and terminal-with-no-output in complete history records a bounded error. Output/cursor/release transactions still use the accepted store batch guarantees. New input beyond the original/confirmed prefix survives.

Exact declared sync receipts confirm the complete offered prefix in the output transaction. Transcript prose/citations and arbitrary tool output never confirm delivery. `syncExposure` is false on the public T3 contract: no harness-specific durable exposure guarantee is assumed. Keep an offer unconfirmed until exact echo; use `confirm_sync` only through a separately established exposure mechanism. Permission replies still require the actual question owner. Message/nonresumable runtime modes are visibly unsupported as live replies and need ordinary board answer/new-input routing.

`quiescence(room, seatId)` returns `{proven,evidence}` for *reported known work*, with provider sequence and local head. It includes runs, queued inputs, attempts, nodes, native child/subagent/tool/command/monitor rosters, PR watches, unresolved child-result deliveries/cohorts, runtime requests, context transfers, local activities, controls and provider holds. A latest terminal run is insufficient. Both `tick` and `quiescence` authenticate the frozen transport and durable observation origin/thread/version/contract. They journal the highest full-snapshot sequence and exact unresolved native keys together with the non-waking hold before applying provider facts. Lower sequences cannot clear known work after reload. A newer missing roster entry also cannot settle a known key: an explicit terminal/delivery/cancellation row or exact association to the same active root is required. Active root exclusion follows exact node/attempt/provider-turn edges, never a status prefix or latest run. Superseded attempts/context transfers are settled source-supported history. These observations are rebuildable journal provenance, not another queue; `quiescence` therefore writes observation facts to the local store while performing only read-only provider I/O.

Opaque background roster IDs have no uniform public completion/wake-delivery acknowledgment. If they disappear, their uncertainty remains held; no timeout or latest terminal state clears them. A later integration needs an exact provider receipt/cancellation/fence for that identity before transfer. A provider proof is not global fencing of unreported external processes. Slice 4 must obtain fresh proof and append transfer against the serialized local state; the existing transfer command additionally refuses all held provider facts. There is no persistent poll lease, native queue or synthetic job.

For adapters without the pinned reserved policy, the same durable native-work check gates a reserved run's first send and every otherwise permitted same-ID resend. A currently idle snapshot cannot authorize a run attempt while `providerObservations[seatId].pending` or its `native_pending` hold remains unresolved. The store rechecks this under the attempt transaction's write lock before recording sending intention; controls can still operate on their exact runtime/run identity while native work remains. Neither preparation nor an absence receipt overrides known native work.

Native child lifecycle and future-wake delivery are separate observations. In the pinned Claude source, completed child/node/item/root rows can coexist with a private wake report awaiting a later continuation. The public adapter therefore retains an explicit `nativeChildWake:<subagentId>` uncertainty key for active or terminal provider-native children. Generic terminal rows, a later terminal root and empty rosters cannot settle it; no uniform public native-child wake receipt/fence is established here. App-owned `completionDelivery`/cohort settlement remains independently supported. A native child needs exact delivery/cancellation/fencing evidence from a provider capability before this key can clear; other harnesses are not granted that guarantee from lifecycle reporting alone.

The production T3 contract is pinned to release `0.0.46-nightly.20261006.2735`, source `fd1c3386c4d60f3477ab3f13c87537848de099f5`. Protocol/version/environment drift fails closed. Source plus read-only member-thread probes establish full projection shapes and transactional *app* command receipt persistence. They do not establish provider execution/tool-effect exactly-once. The public RPC returns only a sequence; receipts have no public read-by-command lookup or authoritative absence API. Interrupted control acceptance is not termination, and a resolved question alone does not attribute a lost response to its command. Command acceptance journals a provider effect before that effect executes; the public projection cannot prove that effect settled, so accepted T3 controls retain a non-waking `control_effect` hold for finish/transfer. Neither final run state nor an arbitrary transcript mention resolves that hold.

3B-I supersedes the former atomic-idle/no-MESSAGE-replay barrier with the accepted reserved-dispatch contract (#273/PASS275). A pinned frozen `start_immediately` reservation can submit one public-shaped MESSAGE, including a busy race yielding the SAME queued or queueHeld native run. Positive frozen-text/message/run binding is tried first; otherwise one identical packet may recover an unknown outcome through pinned durable app dedupe. The SQLite attempt guard rechecks frozen policy, origin, full checkpoint and the two-packet bound. The adapter rechecks descriptor and frozen bytes immediately before RPC. No queue.resume, replacement run, new retry IDs or timer-created work exists. Restored/deleted provider state is outside the pinned persistence assumption; detected origin, sequence, partial-history or content drift holds visibly. This is app receipt dedupe, never provider/tool-effect exactly-once.

Unknown or accepted live controls still hold their fixed original causal requests (and their ancestors) across runs. Registered background and unclassified native invocation work remains held until original results are recorded. Unsettled native response/wake delivery holds reseat. Independent real input can reserve after the old dispatch ends despite fixed work/reseat holds; strict adapters retain their native-idle transport barrier. Terminal/empty native rosters never settle logical background work.

Additional reproducible gates: `node --no-warnings=ExperimentalWarning --test --test-timeout=20000 tests/engine/{provider-http,reconciler,provider-faults}.test.ts`. These run the actual HTTP/RPC adapter, reconciler and SQLite store against isolated source-shaped stubs and an explicitly fake stronger contract. Real SIGKILLs cover frozen/sending bytes, acceptance before local receipt, control receipt loss and output before terminal observation. No real provider turn, production database mutation, service restart or browser cutover occurs.


3B-I local protocol and stage4 interface

The additional authoritative events record scoped capability fingerprints, ordinary full results, closed local-operation receipts and exact native bindings, activity-operation receipts, native run status and retained source conflicts. Each exists to preserve a specific invariant: authenticate an original generation; freeze causal result/outcome; replay original member intent without repeating effects; separate local completion from native response delivery; or retain changed evidence before transfer. They fold into the existing four disposable indices; there are no new tables, work queues or independent state machines.

Host sequence: `store.reserveNative(room, seat, budget)` allocates random UUID run/command/message IDs; `reconciler.prepareRun` freezes the prefix/model/pinned wire; `protocol.authorizeRun(room, runId, {generation,server})` journals the capability hash before launch and returns a bearer credential ONLY to trusted tool configuration. Freeze checks prevent command/message reuse across rooms sharing this store/environment. Stage4 must provision the returned secret in trusted MCP transport, expose the original run ID already present in the frozen envelope, and route authenticated HTTP Requests to `EngineLocalProtocol.handle(room, request)`. This slice starts no listener, installs/configures no MCP server and changes no live service. Member input contains no actor/trusted boolean or receipt authority.

`POST /operations` takes `{itemId,intent}`. Exact native MCP arguments are the intent alone: schema `backroom.operation.v1`, stable clientId, nonce, originRunId and operation-specific fields. `own_run_view` supplies at most16 ordinary item/digest/status references (offset pagination never confirms delivery). `consume_tool_result` takes explicit `toolRefs[{itemId,digest,requestIds}]`. `finish` adds body and explicit disposition, with optional ordinary toolRefs. Native source must match configured server/tool provenance, exact argument/nonce, immutable thread/run/root/node/nativeRef and attempt ordinal. The first closed local MCP projection subset is pinned Codex; other native provenance/response projections fail closed until separately audited. The MCP bridge must return the exact HTTP body as structuredContent (Codex preserves it directly).

Authenticate, serialize raw-intent receipt lookup BEFORE any fresh contract/snapshot/detail read, then replay the original response verbatim. On first commit, SQLite validates current checkpoint/source under its writer lock and appends recorded results/effects, own bindings and actual finish claim outcome with the receipt atomically. Same-raw-intent concurrent packets replay one original receipt even with different native aliases. Exact node/item edges clear only that invocation. No consume-of-consume: these three closed handlers commit all their local work before returning, leaving native response delivery as reseat uncertainty. `{recorded:true}` means committed evidence, not an answered claim. A pending_activity/superseded/late result never silently upgrades on retry. Native root release still requires terminal plus imported explicit output; later finals remain visible.

`POST /activities` uses schema `backroom.activity.v1` with the same stable identity/nonce/origin, activityId and activityGeneration. `register_activity` adds requestIds and nativeId (null if not available); it must commit before native launch and registers no provider work itself. An unknown nativeId remains pending until the HOST calls `await protocol.bindActivity(room, activityId, {nativeId, generation})` with the exact preallocated native ID, before launching it. The binding is immutable, journaled under the writer lock, and rejects any ID observed earlier (even if subsequently omitted) or registered to another activity. A result from the same run, generation or time window cannot substitute for this binding. V1 retains this strict prelaunch rule. The separate member-declared v2 API below supports IDs returned only after launch without changing v1 authority or receipts.

`record_activity_result` adds an original-generation lossless toolRef, body, completion(done|failed) and explicit disposition. It requires the bound exact native ID and commits source/result, logical settlement, actual claim and raw receipt atomically. Authenticated activity operations are classified by their own committed local receipts, as are the three ordinary local operations. Their response delivery remains separate reseat uncertainty. They never require consumption of their own receipt. A HOST capability with explicit activityId/nativeRunId authorizes a native continuation to record the original activity result, independent of subsequent Backroom runs; no latest-run association is inferred. Native wake delivery remains separate after logical settlement.

Accepted runtime control state and its fixed causal `control_effect` hold commit in the same batch. App acceptance alone cannot settle the affected request, including immediately after process recovery; a proven effect can clear the hold separately. Missing native receipt response/detail after known local effects remains a reseat hold, permitting independent new input after the original root ends. Changed original intent/source identity retains a causal conflict before fresh local effects or claims; replay of an already committed raw intent still precedes all provider reads. Unsupported native tool items retain causal node work through terminal lifecycle and cannot be hidden by an unconsumed item alias. Native attempt origin is validated through the pinned run/root/provider-thread/turn edges; the actual RunAttempt has no threadId field.

Already classified sources retain unsupported item-kind changes and actual node-side origin evidence. Exact aliases require consistent run, root, provider thread/turn, attempt, generation and native reference. Reconciliation compares current snapshots and returned details with the original binding before treating any failure as response availability, then imports the latest checkpoint before new local effects. Ordinary results must retain their recorded terminal lifecycle and exit code even when output is absent; a running native node also restores a causal hold. Known closed local effects keep a separate response hold when an otherwise intact node awaits delivery. Contradictory source projections remain attached to their original recorded run. Runtime-control holds match exact complete control IDs, including IDs with shared prefixes.

Code correctness is separate from final comparative adoption. U permits positive ordinary invocation closure with honest available evidence and explicit member-declared postlaunch bindings. It retains strict optional consumption and all known independent work, control, delivery and reseat holds. Accepted P storage behavior remains incremental with whole-room cold/foreign/corruption audits; warm append timing does not describe cold reads, full serialization or provider latency. Stages4/5 remain unwired and gated on independent code and comparative approval.

Every ordinary consumption ALWAYS invokes actual getTurnItem, twice bracketed by three complete monotone snapshots, and a final origin check. Only positively lossless input AND output each <8192 UTF-8 serialized bytes are supported: command strings with exact integer exitCode, or finite JSON for dynamic tools with present output (null/empty/whitespace allowed). Actual truncation/unserializable markers, image/opaque shapes, withheld/partial/summary flags, unstable identity/generation/outcome and unavailable detail retain visible source/availability holds. No snapshot output is hashed as a full result, no evidence is silently truncated/consumed. Original source content remains at T3 for unsupported large/binary values. Receipt-backed outputs are revalidated even after confirmation; changed bodies are journaled as durable conflicts before quiescence, without undoing known effects. Already recorded ordinary results retain analogous conflict checks.

Stages4/5 remain: production API/tool authentication provisioning and UI, then whole-room browser integration, legacy queue removal and cutover. Unknown live effects, provider-authorized queueHeld recovery and unfenced native child wakes remain explicit availability limits. Large/image/edit payload availability is exposed separately from invocation closure; strict byte consumption remains limited to its supported original subset. Tests use real local HTTP adapter/Request handlers and SQLite transactions with a simulated T3 server; process-loss injections are real SIGKILLs. No live/paid provider validation or deployment is claimed.

Result validation covers the final observed revision/outcome of every relied-on source, including earlier sources superseded during later detail reads. Each known source has at most two validations in one call. Result detail must cover the exact final native snapshot sequence: native timestamps alone are not unique revision tokens. A final newer sequence keeps an explicit original-result work hold or closed-own-response reseat hold; one-time benign revisions can settle after bounded revalidation. Fresh ordinary and registered activity result details must also match that final sequence under the writer lock. Native own changed bodies remain durably visible before transfer, including unsupported delivery forms. There is no timer or automatic self-wake. Operation/activity packets include a host-collected hash of the final source metadata, checked under the SQLite writer lock with the sequence and individual source fields; it is never accepted from member input. Raw original receipt recovery still precedes these checks and all provider reads. Quiescence declines a superseding concurrent source/journal checkpoint. Continuous unrelated native changes may exhaust bounded validation and temporarily hold completion or reseat; this is an availability limit, not an assertion that a timestamp proves unchanged output.

Ordinary consumption requires matching terminal node/item outcomes (completed, failed, cancelled or interrupted). The exact node outcome is included in the result digest and compared after consumption independently of output availability. Known closed own effects can retain mismatched native delivery as reseat uncertainty. First authoritative native observations and holds preserve an invocation's original association even before consumption, across restoration/restart/index rebuild. Later projections cannot move that invocation onto a newer run. Fresh local effects, ordinary consumption and registered-result settlement also recheck that original native identity under the writer lock; a rejected call remains native work until its actual coherent invocation outcome is recorded; synthetic interruption and missing command exit codes cannot provide that closure. These guards add no queue, durable table or live caller, and do not change the separate common-flow adoption limits.

The second actual detail read covers only its preceding native snapshot floor. A later metadata snapshot cannot relabel that earlier body with a newer sequence, even when timestamps collide; intervening native progress rejects the detail. Known results get at most one additional validation, and an invalidated proof remains held if that bounded reread is unavailable. Ordinary uncertainty retains original work scope; closed own response uncertainty retains reseat scope. Node-first history separately preserves its first native origin, first item kind and first established complete item identity/input/provenance. Later complete evidence enriches the original node rather than exempting future input or intent changes.
