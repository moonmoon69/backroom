# Working in Backroom

The habits of every agent working in this repository, whoever assigned the work.

- Before you report ready, review your own diff (with a subagent or a review workflow, if your harness has one) and fix what it finds.
- Turn every review finding into a test that fails without the fix: a unit test where one can show it, a rehearsal state only for focus, scroll or layout.
- Build and rehearse in a worktree of your own (`git worktree add`), never in the checkout the live service runs from: `npm run build:web` there swaps the user's live page for your unfinished work, and for anyone else's in that checkout.
- Run the checks before you report ready, in that worktree; say what you ran and what it printed, and name any check you skipped:
  - `npm install` first (a fresh worktree has no `node_modules`);
  - `npm run check` (the service's types, and the tests, which run against the fake T3 adapter);
  - `npm --workspace web run typecheck` when the page changed (`npm run check` does not cover `web/`);
  - browser rehearsals only when the change reaches the page (`web/`, the engine, host or routes the page reads, or the rehearsal scripts), none for docs, test-only changes or internals the unit tests cover: `npm run build:web`, then the step that covers the change, once: `node scripts/rehearse.ts --step ui|room|keys --as <your rooms-browser key> --port <a free port>` (keys for keyboard, focus, scroll and layout; ui and room for what the engine and the page show), or all three when unsure, started together with `--step all` (ui on that port, room and keys on the next two, keys in a browser of its own, `--keys-browser`, default backroom-dev, ui and room in `--browser`, default general), which prints each step's result and exits non-zero if any failed. Each step starts a throwaway service of its own (`ROOMS_ADAPTER=fake`, its own data folder, named by its port) on the page just built, never the live service on :4400 or the user's rooms;
  - a new or changed state proved three times on its own with `--only <state>` (its number, part of its name or a /pattern/; `--list` prints a step's states), which plays only what the states named depend on (from the section of the first of them on, the states before each without their screenshots and console reads) and stops after the last, then once in the step's full run; for a state that needs the whole story before it (ui 1-12 and room 1-14, as the README lists), `--until <state>` instead, which plays the step up to it with every check on;
  - a fails-without-the-fix proof is a unit test where one can show it; else, in a worktree of the fix's commit (whose scripts have the flags and the state), the fix taken out of the product with `git checkout <the commit before the fix> -- <the files of web/ or src/ the fix changed>` when the fix is the last change to those files, else with `git show <the fix's commit> -- <those files> | git apply -R`, and a file the fix adds deleted; then `npm install`, `npm run build:web` and the state with `--only`: it must fail at that state;
  - never rerun a green step's full run to see it pass again: a flaky state is fixed or cut, not repeated;
  - after merging main, `npm run check` again, and a step again only if the merge touched what it covers.
- Reviewers run `npm run check` in a worktree of their own, read the writer's gate logs and screenshots, run once the step the change targets (`--step all` when unsure, or its new states with `--only`), and spend the rest of the review trying the change by hand on a throwaway service.
- End every answer with a Handoff: the paths, the branch and the commit where your work is, and anything left unintegrated.
